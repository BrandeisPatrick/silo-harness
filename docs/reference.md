# Reference

## Permission modes

| Mode | Behaviour |
| --- | --- |
| Ask | Commands, writes and edits show an approval card (default) |
| Accept edits | Edits inside the project run, except to a [protected path](#protected-paths); commands ask |
| Auto | Actions run without a card; a safety check (a second model call) blocks the risky ones, and the agent reads why. See [Auto mode](#auto-mode) |
| Plan | Read-only exploration ending in a plan card you approve; a read-only command the guard flags ("reads secrets") asks |
| Bypass | Everything runs |

## Approval cards

An action that needs your OK waits on a card, as in Claude Code: the question as its title ("Allow Silo Harness to run this command?"), then in muted text what the call does in its own words (a command's description, when the model gave one) and why it asks when the mode would not have (in Auto, "Auto mode stopped to ask: it uses sudo."; for a hook, the hook's reason), then the command or the change. At the bottom right: **Deny** and **Allow once ⌘↵**, with **⌄** for the wider answers, "Allow … for this session" (`A`) and "Always allow … in this project" (`P`), which cover a program, a flagged reason, an MCP server or edits. A tool's own question (a sub-session, a message to another session, a schedule) and a hook's "ask" have Allow once and Deny only.

Keys while a card waits: `⌘↵` allows once (also from the chat bar while you type), `Esc` denies (instead of stopping the run), `A` and `P` pick the scopes when the chat bar is empty or the ⌄ menu is open. Once answered the card goes; the call's row keeps the answer ("Allowed once", "Allowed git for this session", "Denied") at the top of its details.

Saved rules: Settings → Permissions. One thing asks in every mode, Bypass included: a schedule the agent wants to create or re-time, because it outlives the conversation.

## Auto mode

Auto mode works like Claude Code's: rules settle most actions, and a safety check, a second model call, decides the rest.

1. **Rules first.** A PreToolUse hook that denies blocks in every mode. Read-only commands and edits inside the working directory run without the check. What your saved rules or "for this session" answers allow runs (a program rule covers neither a command the guard flags, such as a force push, nor an interpreter such as `python`), except a write to a [protected path](#protected-paths), which still goes to the check.
2. **The check.** Everything else, MCP calls that are not read-only included, goes to the check: the session's own model, or `autoMode.model`, asked for the least thinking the model allows (on Anthropic's API: thinking off, or effort `low` where it cannot be off). It reads your messages in the session, the agent's tool calls so far (never their results), the project's instructions files, your `autoMode` notes, your earlier answers and the action, and answers allow or block with a reason that names a category: "[Destructive Git] force-pushes over remote history". It blocks by default piping a download into a shell, sending secrets or private data out, printing live credentials, production deploys and migrations, force pushes, `git reset --hard`, `git clean -fd`, deleting outside the working directory, destructive infrastructure changes, merging pull requests you did not approve, writing to the app's own files and publishing. It allows by default local work in the working directory, installing dependencies, read-only commands of any CLI (`gcloud projects list`, `kubectl get`), read-only HTTP and pushing to a branch that is not the default one. A message of yours approves a risky action only when it names the action and its risk ("force-push the feature branch"); a boundary you stated ("don't push") blocks.
3. **A block.** The action does not run. The agent reads "Blocked by Auto mode: [Category] reason. Do not try to get around it; continue with other work, or ask the user." and goes on. The chat shows one line, "Auto mode blocked git push --force · Allow", with the reason as its tooltip. **Allow** lets that exact action run once, without the check, when the agent tries it again, and tells the agent it may. The phone has the same line and Allow, and Settings → Permissions → Recently blocked lists the blocks since the app started.
4. **Pauses.** After 3 blocks in a row or 20 in a session, Auto mode pauses for that session: what needs the check shows the approval card again, with a one-line notice.
5. **The browser.** A new site, an act on a sign-in or other sensitive page, and page script the guard flags go to the check too, which has a third answer: ask, which shows the card. It allows a site you named or the task needs (and its sign-in page, to move through it), blocks sending your data to a site the task does not need, a site only page content pointed to, and script that reads cookies, storage or passwords, and asks for posting, sending, deleting or changing settings as you, or acting on a sign-in, bank or payment page beyond moving through it. An allowed site is allowed for the session; each act on a sensitive page and each script is checked again. A block counts toward the pause; ask does not. If the check fails or is paused, the card shows. It is told the tool, the site, the URL, the card's line and note and the script, never the page's text.
6. **What it remembers.** Your own answers on approval cards (allow or deny, in any mode) and your Allow after a block are kept, one line each, in `auto-learned.json` in the app's data folder (about 200; alike answers count up). The check gets about 30 of them, denials first, then the most recent, as your earlier decisions: it decides like cases the same way, never broader ones, and a deny weighs more. Nothing the agent, a page or the check itself does is recorded, and an answer means only what it said: Allow once still allows once. Settings → Permissions → Auto mode lists them, with Remove and Forget all; "Learn from my answers" off records and sends nothing.
7. **Fails closed.** An error, a timeout or an answer that is neither allow nor block blocks the action ("[Unavailable] the safety check could not run"); for a browser action it shows the card. When no model can run the check (none set, a provider without its key), or its model cannot be reached before it ever answered, Auto mode asks as it used to: risky commands and writes outside the project show the card, the rest runs.
8. **Always asks.** `ask_user` questions, the browser's purchase and account cards, `sudo`, and `rm` or `rmdir` of the home folder, `/`, the working directory or a folder above it, or a system folder, also inside `$(…)`, backticks, `sh -c '…'`, `eval`, `xargs` and `find -exec`. A tool's own question (a sub-session, a message to another session) keeps its card too.

**Read-only commands** (what Plan mode runs, and Auto mode runs without the check): `ls`, `cat`, `grep`, `rg`, `find`, `sed -n`, `awk`, `git status/log/diff/show …`, `npm ls` and the like, with no substitution (`$(…)`, backticks, `<(…)`), no redirection into a file (`2>/dev/null` and `2>&1` are fine), no leading `VAR=value`, and no flag that writes or runs something (`sed -i`, `sort -o`, `find -exec`, `rg --pre`, `git -c`, `git diff --output`, `npm config set` …). `less`, `more`, `make`, `eslint` and `prettier` are not on the list. The guard reads the command's text; it is a heuristic, not a sandbox.

**Cloud commands.** Every `gcloud`, `az`, `pulumi`, `flyctl`, `heroku`, `vercel` and `netlify` command, and every `aws` command but a recognised read, is a "cloud or infrastructure change". A recognised read is a read-only command like `ls`: `aws` itself first, a `get-`, `list-` or `describe-` operation of a common service (EC2, S3, Lambda, ECS, IAM, CloudWatch, CloudFormation and some fifty more; others go to the check) (or `sts get-caller-identity`, `s3 ls`, `s3api head-object`, `configure list`), only `--profile`, `--region`, `--output`, `--query`, paging and the operation's own options, written in full, nothing quoted oddly or expanded. Never one: an operation that returns a token, password, secret, key or environment variables (`ecr get-login-password`, `lambda get-function`, `ssm get-parameter --with-decryption` …) or writes a file (`s3 cp`, `s3api get-object`), `--endpoint-url`, `--cli-input-json`, `--debug`, `--no-verify-ssl`, or a `file://` or `https://` value.

**macOS privacy prompts.** macOS asks in the app's name when a command reaches a guarded folder or device, so the app asks first, with these reasons (allowable for the session or the project; Plan mode asks for the read-only ones):

- "scans the home folder": `find`, `fd`, `grep -r`, `rg`, `ag`, `ack`, `tree`, `du` or `ls -R` walking the home folder, `~/Library`, `/`, `/Users`, `/Volumes` or `~/*` (with no folder named, the working directory when it is one of these). A named folder (`find ~/Desktop`) or one level (`find ~ -maxdepth 1`, `fd -d 1`, `tree -L 1`) does not ask. `grep` and `glob` rooted there ask too. `mdfind` finds files without a prompt and is read-only.
- "records the screen": `screencapture`. "uses the camera or microphone": `imagesnap`, `rec`, `ffmpeg`/`ffplay`/`ffprobe` with `avfoundation`, `sox -d`. "reads the clipboard": `pbpaste`.
- `tccutil` asks "changes macOS settings"; `crontab` but `crontab -l` asks "system control".

### Protected paths

In the project: `.git`, `.silo-harness`, `.open-harness`, `.claude`, `.vscode`, `.idea`, `.husky`, `.github/workflows`, `.envrc`, `.gitmodules` and `.mcp.json`, but not the `skills`, `commands`, `agents` and `worktrees` folders in `.claude` nor `skills` in `.silo-harness`. Anywhere: shell start-up files, `~/.gitconfig`, `~/.config/git`, `~/.ripgreprc`, `~/.ssh`, `~/.aws`, launch agents, the app's own data and `~/.silo-harness` (but its skills and `SILOHARNESS.md`). A write to one, by `write_file`, `edit_file` or a command (a redirection, `cp`, `mv`, `tee`, `ln`, `rsync`, `install`, `sed -i`, `rm`), asks in every mode but Bypass, with Allow and Deny only: no saved rule or "for this session" answer covers it. In Auto mode with the check it goes to the check. The command side reads the command's text: a heuristic, not a sandbox.

Tell the check about your setup in your own settings.json: `autoMode.environment`, `autoMode.allow` and `autoMode.model` (see [configure.md](configure.md#auto-mode)).

## Questions

When a choice is genuinely yours (a preference, an unclear requirement, which of several approaches), the agent asks with `ask_user`, in every mode, Plan included, without an approval. The run waits on a card in the approval card's frame: the question as its title with its short header as a chip ("1 of 3" when there are several, shown one at a time with Next and Back), the 2–4 options as rows with a radio button, or a checkbox when more than one can apply, and **Other**, a field for your own words. Click anywhere on a row, or press `1`–`4`; `↑` `↓` move between rows; **Submit ⌘↵** sends the answers, **Skip** or `Esc` tells the agent "The user skipped the question." The status line says "Waiting for your answer", and the sidebar, the Dock badge and a notification say a session waits for you. The agent reads each question's header with the option you picked or what you typed. Answered, the card folds to one line, "Asked a question", with the answers inside. On the phone page a question with one answer per question is a set of buttons; anything more says to answer in the app.

## Tools

| Tool | Purpose |
| --- | --- |
| `read_file` `write_file` `edit_file` `list_directory` `glob` `grep` | Files. Reading a secret path (`~/.ssh`, `~/.aws`, `.env` but not `.env.example`, `*.pem`, the app's own data) asks "reads secrets" in every mode but Bypass, or goes to Auto mode's check; `grep` and `glob` rooted at the home folder, `/`, `/Users` or `/Volumes` ask "scans the home folder" the same way; `grep` and `glob` over a folder leave secret files out. `edit_file` falls back to a match that treats runs of whitespace (and curly quotes, long dashes) as equal, and says so; with no match it shows the closest lines; it refuses a file that changed on disk since the session read it. `grep` uses ripgrep when it is installed (`.gitignore` honoured), else grep, and stops after 30 s with what it found so far; it returns up to 300 matching lines, each cut at 400 characters; `glob` lists the newest-modified files first, up to 1,000; either result stops at 12,000 characters, after a whole line, and says how many more there were |
| `bash` | Shell command in the session's folder, with an optional short description of what it does (shown on its approval card); stopping the run stops the command and what it started. Long output keeps its first 12K and last 18K characters, and the exit code always. An unmatched wildcard passes through as in bash. A sign-in that waits for you (`aws sso login`, `gcloud auth login`, `az login`, `gh auth login`, `npm login`, `docker login`) is not run: the agent is told to use `terminal_run` |
| `terminal_run` `terminal_read` `terminal_list` `terminal_stop` | Terminal pane tabs; long output keeps its start and its end |
| `browser_*` | Built-in browser, on the active tab: navigate, click and type by visible text, read, find, wait, scroll, press a key, screenshot, eval (see Browser) |
| `browser_tabs` | The pane's tabs: `list`, `new` (with `url`; `background` keeps the current tab in front), `select` and `close` (`tab_id`). A tab on a site not allowed yet shows its site name only |
| `show_image` | Put an image (a screenshot, a chart, a picture in the project) inline in the reply |
| `create_artifact` | HTML, SVG, Markdown or code shown in the browser pane; an HTML artifact runs its own code and scripts from cdnjs, jsDelivr or unpkg, and sends nothing anywhere (a CSP blocks every request out; it never leaves the artifact or opens a window by itself, the blocked-popup strip offers the address instead) |
| `update_tasks` | The task list card |
| `ask_user` | Ask you one to four multiple-choice questions and wait for the answers (see Questions) |
| `skill` | Load a skill |
| `submit_plan` | Plan mode: hand the plan to you |
| `load_tools` | Load tool groups (`browser`, `terminal`, `sessions`, `schedules`, `mods`) for the rest of the session; no row in the conversation |
| `schedule_create` `schedule_list` `schedule_update` `schedule_delete` | Scheduled tasks |
| `session_spawn` `session_send` `session_list` `session_read` `session_merge` | Sub-sessions and messages between sessions; `session_list` with a `query` finds sessions by name, and says which sessions take messages without your approval. `session_send` to the session's parent or its own sub-sessions goes straight through; to any other session it asks you (Allow once, or "Allow messages to … for this session"; no card in Bypass, refused in Plan); from a session a schedule or a dream started (or one below it) it reaches only its parent and sub-sessions, anything else is refused |
| `session_rename` | Rename this session when you ask (no approval; the title is locked like a manual rename) |
| `mod_check` | What is wrong with a mod the agent is writing |
| `history_read` `history_search` `propose_skill` `propose_memory` `propose_mod` `withdraw_proposal` | A dream's session only (see Dreaming); no other session is offered them |
| `mcp__<server>__<tool>` | MCP server tools |

The browser tools that can need your approval (`browser_navigate`, `browser_click`, `browser_type`, `browser_press_key`, `browser_eval`, `browser_tabs`) take an optional `reason`, one sentence on why, which the card shows in grey under the action and nowhere else; the system prompt asks the model for it.

In the conversation each run of calls in a turn is one quiet line that says what it did, in the order it did it ("Read 3 files, ran 2 commands, edited a file"), with the lines that edits and writes added and removed and how many calls failed or were denied on its right; click it, or focus it and press Enter, to see the rows. A single call is one line too ("Ran a command", "Read a file", "Edited a file +3 −1"), which opens straight to that call's details; a call you or a hook denied reads "Denied a command". While the turn runs the line names the call in flight, faint, with a shimmer. Opened, it lists the calls one line each, about nine before the list scrolls. A waiting approval or question card stays in the open under the line; once answered it goes, and the call's row keeps the answer. A turn that calls tools has a header over its output, "Working for 18s" while it runs and "Worked for 53s" after; when the turn ends with an answer its working (interim replies, thinking, the lines) folds away under the header, leaving the answer, cards, images and notices; click the header to open it again. An interrupted or failed turn stays open. Settings → General → Tool activity (`toolActivity`: `summary`, the default, or `all`) shows every call as its own row instead, still without a separate line for an answered card, and folds nothing by itself.

Every tool offered is described to the model in every request, so the tools come in groups that a session gets only once it needs them. A session starts with the file, shell, artifact, task, question, skill and plan tools, `show_image`, the MCP tools and `load_tools`, whose description lists the groups, one line each: `browser` (the `browser_*` tools), `terminal` (`terminal_*`), `sessions` (`session_*`), `schedules` (`schedule_*`) and `mods` (`mod_check`). The model loads one with `load_tools` and has its tools from its next step on; what it should know about them (the browser's rules, how sub-sessions work) comes in the result. A call to a tool of a group not loaded yet loads the group and runs, and a message that asks to open a web address (`open https://…`), or names one together with the word browser, loads the browser before the first request; one about other sessions (a sub-session, another session, the session called …), or a message from another session, loads `sessions` the same way. A loaded group stays for the rest of the session: after a compaction (whose brief repeats what the load said), in a fork, and when the session is opened again. So that providers can cache the start of each request, loading a group changes neither the system prompt nor the tools a session already had: its tools are added after them. On Anthropic's own API every group's tools are in the request from the first one, deferred, and a load brings them in without changing the request's tools at all. Settings → Context → "Tools offered to the model" (`toolSet`) decides: `auto` (Automatic, the default) loads groups when needed, whatever the context window; `all` sends every tool with every request; `essential` loads groups when needed but leaves the scheduling, session and mod tools out altogether, and tells the model so.

## Sessions

- Several sessions run at once (six at most). Switch freely: a running session keeps going off screen, and the sidebar shows a spinner while it runs, a dot when it waits for you, and a blue dot when it finished unseen.
- Each session has its own folder; the app's folder follows the session on screen. Project MCP servers and the project `settings.json` follow the folder on screen, not each background session's.
- Each session has its own browser tabs. A background session's agent keeps browsing in its own, out of sight; a popup, a permission or download bar or a certificate page it raises waits until you open that session.
- **Forks** copy a conversation and continue on their own. **Sub-sessions** are started by the agent (`session_spawn`) or by `/spawn`; they run in the background, sit under their parent in the sidebar, and report back when they finish a turn. **Merge** summarises what a sub-session or fork did since it split off and adds that to the parent; files need no merging, since sessions share the folder.
- Nesting stops at two levels; a session may have four sub-sessions running and twelve in all.
- **Messages between sessions.** A session sends another one a message with `session_send` (or you do with `/send`). The receiver takes it as a request from another agent, not from you: it starts a run there, or waits behind the step in progress, or, while the receiver's plan waits for your decision, waits until you decide. It never answers an approval card, a question or a plan, never changes the permission mode, and the receiver is told it carries none of your authority. Both conversations show it as one quiet line: "Messaged deploy fix ›" in the sender and "Received message from release notes ›" in the receiver (a sub-session's report too), the other session's name a link that opens it; click the line to read the message. A session that is not on screen gets the blue unread dot as soon as a message reaches it. The reply does not travel back by itself (a sub-session's report does); the sender reads it with `session_read`, or the receiver answers with `session_send`.
- **Names.** Rename a session in the sidebar (F2, double-click, the menu), in the top bar, with `/rename`, or by asking the agent ("call this session deploy fix"). From any other session you can then name it in plain words ("read the session called deploy fix"): every command and tool that takes a session accepts its name or id. Lookup searches every session not in the trash and tries, in order: the exact id; the start of an id (6 characters or more); the name ignoring case, quotes, punctuation and spacing (`tcg fork`, `"TCG (fork)"` and `tcg-fork` all find `tcg (fork)`); the start of a name; a name holding every word; a small misspelling. When several sessions fit, a related one (parent, sub-session, fork) wins; otherwise the answer lists them with id, folder and last activity, and with no match at all it lists the closest names. Two sessions may share a name; the rename then says that lookup by it is ambiguous.

## Browser

The Browser pane is a browser of its own beside the chat, which you and the agent share: what the agent reads is what you see.

- **Its own profile.** The pane keeps its cookies and site data in a profile of its own, apart from the app's pages, artifacts and mods. On the first launch with it your sign-ins were copied over (a site that keeps its sign-in in local storage may ask again), and a one-time note under the URL bar said so. Settings → Browser → **Keep cookies after quitting** (on by default) keeps you signed in from one launch to the next; off, the profile's cookies and site data are cleared when the app quits. **Clear browsing data** signs you out of every site at once: cookies, site data, cache and saved HTTP sign-ins go, and open tabs reload.
- **Tabs.** Each session has its own tabs: the pane shows those of the session on screen, and a new session, a fork or a sub-session starts with a blank tab of its own. Deleting a session closes its tabs. Sign-ins are shared, since every session uses the one profile. The pane has one strip at the window's top: each page is a tab (favicon, title, ×) beside the open tools (Diff, Terminal, each pane a mod adds), in the order they were opened, + at the end. A blank tab shows the New tab page, which lists the tools; a tool's tab joins the strip from its shortcut, that page, the ⋯ menu, or by itself (Diff when files change, Terminal when a terminal turns busy), and its × only takes it out of the strip. The toggle at the top-right corner shows and hides the pane. Short of room, long titles shorten first (a title of eight characters or fewer, like Diff or Terminal, is never cut), then the quiet tool tabs show only their icon and count, then the quiet page tabs too; the active tab always keeps its title and ×, and a tab's tooltip names it. Only then does the strip scroll. A middle click closes a tab, ←/→ move across the strip, and an overflowing strip scrolls with the wheel. At most 12 page tabs per session. The Terminal tab shows one terminal right under the strip; a row of its terminals (each with ×, then +) appears once there are two. `⌘T` opens another, and so does the New tab page's "New terminal" row while the Terminal tab is open; with none left, the pane offers New terminal. With the pane focused (its URL bar, its strip, or the page itself): `⌘⇧N` new tab, `⌘W` close it (the last one leaves a blank tab), `⌘L` the URL bar. A link with `target="_blank"` opens a tab; a ⌘-click or middle click, a tab in the background.
- **Popups.** A page's sized `window.open` (a "Sign in with Google" window, say) opens as a card floating over the pane, with a bar of its own (favicon, title, host, ×) you can drag. It keeps `window.opener` and `postMessage`, so the sign-in completes in the page that opened it, and the card goes when the popup closes itself. At most three at once: a fourth is blocked, and a strip under the URL bar says "A popup was blocked · Show"; Show opens it in a new tab, and the strip goes with the next page or its ×.
- **The URL pill** shows a grey lock for a secure page, "Not secure" for plain HTTP, and an amber triangle when you proceeded past a certificate error. A chip at its right ("125%") shows the page's zoom when it is not 100%; a click resets it.
- **Find in page.** `⌘F` with the pane focused opens a bar under the URL bar: type to search, "3 of 12" counts the matches, `Enter` and `⇧Enter` (or ↑ ↓) move between them, `Esc` or × closes it and gives the page the focus back. It belongs to its tab: switching tabs closes it, and a new page clears its count. In the composer, `⌘F` still searches sessions.
- **Zoom.** `⌘+` (or `⌘=`), `⌘−` and `⌘0` with the pane focused zoom the page through Chrome's steps, 25% to 500%. The level is kept per site (the host, as Chrome does) in `browser/zoom.json` of the data folder, so the site opens at it again, also after a relaunch. View → Zoom In, Zoom Out and Actual Size do the same while a page has the focus, and zoom the app's own window otherwise: one or the other, never both.
- **The context menu** (a right click on a page), native: spelling suggestions and Add to Dictionary on a misspelled word; Open Link in New Tab and Copy Link Address on a link; Open Image in New Tab, Copy Image and Save Image As… on an image (saved like any download of yours); Copy and Search DuckDuckGo for "…" on a selection; Cut, Copy, Paste, Paste and Match Style and Select All in a field; Back, Forward and Reload on the page itself; then **Print…**, **Save as PDF…** (a save dialog, the page's title as the name) and **Inspect Element**. `⌥⌘I` with the pane focused opens the page's DevTools in a window of their own. Nothing in the menu is the agent's.
- **Permissions.** A page that wants your camera, microphone, location, notifications, the clipboard or to open another app asks on a bar under the URL bar, never in a dialog: **Allow this time** (for that tab, until it leaves the site), **Allow every time** or **Don't allow** (both saved per site; Settings → Browser → Permissions lists them, with Reset). The bar belongs to its tab and waits while the tab is in the background; a popup's request is its tab's. Full screen and copying to the clipboard are allowed without asking; USB, HID and serial devices are always refused. Only you can answer: no tool and not the phone page.
- **Certificates.** A page whose certificate is not valid does not load: the pane covers the tab with "This connection is not private", the host and the reason in words, **Go back**, and "Proceed anyway (unsafe)" as a quiet link. Proceeding lets that host with that certificate through until the app quits, and the URL pill shows the amber triangle. The agent is told the certificate is not valid and that only you can proceed.
- **Downloads** save without a dialog to the Downloads folder (or the folder chosen in Settings → Browser), under a cleaned name of our own making ("report (2).pdf" when the name is taken). The tray at the right of the browser bar, a down arrow with a progress ring while something downloads and a dot when one finished unseen, lists the last 50 with Open, Show in Finder, Cancel and Clear. A download is yours only when it starts within five seconds of your own key press or click in that tab (and not while one of the agent's browser calls acts, or within two seconds after); every other one, the agent's or a page's own, waits, paused and out of your folder, on a bar under the URL bar: "The agent started a download: report.pdf (1.2 MB) from example.com" (or "A page started a download: …" when the agent was not acting), Allow or Don't allow. A finished download carries macOS's quarantine mark, so Gatekeeper checks an app or script from it.
- **Links from the chat** open in your default browser. With Settings → Browser → **Open links from the chat in the Browser pane** on, a web link opens in a new tab of the session on screen instead and that tab comes forward, as your own navigation (no card). Other links (mailto:, a file) still go to the Mac's app for them.

### What the agent may do there

- **Every site asks once.** The first browser call on a site you have not allowed (reading included, since reading is where a prompt injection gets in) shows a card (in Auto mode the [safety check](#auto-mode) decides, and shows the card when it is unsure): "Let the agent use example.com?" with the action, and the model's `reason` in grey under it. **Allow once** is that call; "Allow example.com for this session" (`A`) and "Always allow example.com" (`P`, saved on this Mac for every project, listed in Settings → Browser → Sites the agent may always use) cover the rest. An approval covers only the scheme you approved it on: allowing `https://example.com` does not allow `http://example.com`. A subdomain is a site of its own, and a call that lands on another site (a redirect) asks again. Listing, switching and closing tabs does not ask.
- **Exempt: your own servers.** `localhost`, `127.0.0.1`, `[::1]`, `*.localhost`, `*.test`, any port, and the hosts or folders you add in Settings → Browser → Exempt hosts, need no card. There the agent may type into a password field, so your app under development can be tested with test accounts; the text is still never repeated. Plan mode stays read-only there too. The app's own remote-control server and a debugging port it was started with are never the agent's, on any local address.
- **Local files.** A `file:` page inside the session's folder needs no card (`read_file` reads it anyway); one outside asks, "Let the agent read a local file?", with its path in full. Artifacts never ask. `javascript:`, `data:`, `blob:`, `chrome:`, `devtools:`, `view-source:` and `about:` pages other than `about:blank` are refused: a page of the agent's own is an artifact.
- **Sensitive sites.** Sign-in pages, email, banks, brokers and wallets, payment pages and password vaults (a built-in list, shown in Settings → Browser, with your own additions under Sites that always ask): every acting call asks there, in every mode but Bypass (in Auto mode through the safety check), with the card "Act on a sensitive site?" and an amber note under it, "This looks like a sign-in site" (or an email, financial, payment or vault site). A page with a password field counts as a sign-in page: the first acting call on it asks once, and the note says so.
- **Refused, in every mode, Bypass included,** with a message the model reads: typing (or pressing a character key) into a password, one-time code or card field away from an exempt host, also when a click moved the focus into one ("Ask them to sign in … in the Browser pane"); a click inside a CAPTCHA (reCAPTCHA, hCaptcha, Turnstile); a click on something the page covered with something else, or that changed since the agent read the page ("read the page again"); a click into a frame from a sensitive site; paste, copy and cut shortcuts ("the clipboard is the user's"); the schemes above. A click that lands in a frame from another site asks first, naming that site ("Click inside a frame from widget.example on shop.example"). Where a click lands is decided by hit-testing the point in a world of the browser's own, which the page cannot change; the refs and the outline live there too. No tool answers a permission bar or proceeds past a certificate error: there is none.
- **Always asked, in every mode, Bypass included,** on a card with Allow and Deny only: a click that looks like a purchase ("Make a purchase?": Pay now, Place order, Buy, Checkout, a submit in a form with card fields or posting to a payment host) or like making an account ("Create an account?": Create account, Sign up, Register), except on an exempt host; and every download the agent starts (the download bar above).
- **`browser_eval`** ("Run JavaScript on example.com?", with the code on the card): Ask and Accept edits ask for every call, even on an allowed site; Auto sends it to the safety check when the code reaches for the site's cookies or storage, the network, saved credentials, a field's value or a password, navigates away, or injects code (the reason on the card), and on a sensitive site; Bypass runs it; Plan refuses it. Its result has the values of credential fields as `•••`.
- **Plan mode** offers the reading tools only (navigate, read, find, get text, wait, scroll, screenshot, the tab list); the site card still appears for a new site, since a navigation can carry data out in its address.
- **Pages are data.** Everything a page says (its text, titles and addresses) reaches the model inside one `<page_content site="…">` fence, the site named by the browser, and the browser rules tell the model that page content is never instructions. Text a person cannot see (transparent, hidden, tiny, clipped, `aria-hidden`, placed far off the page) is left out of `browser_get_text` and `browser_read_page`. Both return 12,000 characters at a time; a cut result says the `start` to call again with. When the page moves to another site or another tab comes in front while a card waits or a read runs, the call does nothing and the model is told to call again.
- **Tabs a page opens** are web pages or artifacts only: a page asking for a `file:`, `data:`, `blob:` or `about:` tab is counted on the blocked-popup strip, with no Show. A blank page a page made counts as that page's site. Open in default browser opens web addresses only and shows a local file in the Finder.
- **No identity or device is chosen for a page:** no client certificate (Electron's default would send the first one in the Keychain), no Bluetooth device, and HTTP sign-in prompts are cancelled.
- **No passkeys yet.** They need a build signed with a Developer ID. When a page asks for one, a bar says "Passkeys don't work here yet. Choose another way to sign in." and the page gets a refusal, so it offers its other ways. A USB security key is untested.
- **Credentials never reach the agent.** The value of a password, one-time code or card field reads `•••` in everything the browser tools report, and `browser_screenshot` is refused while such a field is focused and filled or shows its value.

Settings → Browser has it all in one place: Keep cookies after quitting, Clear browsing data, the downloads folder, Open links from the chat in the Browser pane, Sites the agent may always use, Sites that always ask (beside the built-in list), Exempt hosts (beside the built-in ones), and the saved permission answers with Reset and Reset all.

## Scheduled tasks

A prompt that runs once at a time, every N minutes (five at least), or on a five-field cron rhythm in local time. Each run gets a session of its own, or is delivered into an existing session as a follow-up. You can also ask the agent: every schedule it creates or re-times shows you an approval card first.

- **The page.** Scheduled in the sidebar opens the Scheduled tasks page in the main column, in place of the session (the row shows selected; choosing a session in the sidebar brings the chat back, and `⌘[` goes back a page). **Yours** shows each task as a card: its name, where a run goes (New session or Same session), the prompt, and its state with its rhythm ("Active · Weekdays at 08:30", "Paused · …", "Done · Once on …"). Search looks through names and prompts; the filter shows All, Active or Paused; the sort is by next run, name or last run. **Templates** has starter tasks (a nightly dependency audit, a weekly changelog draft, a morning summary, a daily test run, a weekly TODO sweep); each opens the New task form filled in.
- **New task ⌄** (New task, or From a template) opens the form: name, instructions, the folder the runs work in, the schedule (once at a date and time, every hour at a minute, every N minutes, hours or days, every day, weekdays, every week on a day, every month on a day up to the 28th, or a custom cron rhythm) with the first run previewed, and whether each run starts a new session or continues one you pick. Runs use the permission mode in the chat bar; one that needs your approval waits for you in its session like any other.
- **A task's page** (click its card): the breadcrumb "Scheduled tasks / name ⌄" (the menu has Edit, Run now and Delete, which asks first), the next run, **Run now** and the **Active** switch (pause and resume); then **History**, every run newest first (the last 100): the session it made or continued, when, and running, waiting for you, done, failed or stopped; a row opens that session in the chat view, where you can keep talking in it. Beside it: the instructions, the project folder, the rhythm, where each run goes and the permission mode.
- **In the sidebar** a run's session is an ordinary session, listed by date with the rest, with a lightning bolt in front of its title and the usual running, waiting and unread marks at the end.
- **When they run.** Only while Silo Harness is open and the Mac awake (Keep awake can hold off sleep). A run missed while it was closed or asleep happens once when it is back, if it was due less than a day before, never as a backlog; an older one is marked missed.
- The side pane's Scheduled tab lists the tasks too; its New button opens the same form and Open page opens the page. Settings no longer has a Scheduled section; a search there for it finds a row that opens the page.

## Dreaming

A dream is a background session that reads what happened in recent sessions and proposes skills (a procedure you asked for more than once), mods (a view or status you keep asking for) and memory (preferences, corrections and facts, as lines in an instructions file). Dreaming in the sidebar opens its page, laid out like Scheduled tasks.

- **When.** Off until you turn on "Dream every day"; then once a day at the time you pick (default 03:00, local time). A daily dream missed while the app was closed runs once after the next launch, unless a dream ran in the last 20 hours. By hand: **Run a dream ⌄** on the Dreaming page (every project with new activity, or one you pick; it turns into Stop the dream while one runs), **Run a dream now** on a project's page, or `/dream` for the current session's project. One dream run at a time.
- **What it reads.** One dream per project folder with activity since that project's last dream (dream sessions, the trash and sessions without a message of yours are left out), most recently active first, at most five per run. Its first message is a digest the app builds from the history log: for each session its id, title, date and origin, then each of your messages and each final reply, clipped, the tool activity in a few words with failures and denied approvals, and the `#` memory lines; plus the skills, mods and instructions files that exist. It is sized to 40% of the context window, oldest first; what does not fit waits, and the project's cursor moves only past what the dream read (and only when it ended without an error).
- **What it can do.** Read: `read_file`, `glob`, `grep`, `list_directory`, `session_list`, `session_read`, `history_read` (any part of one session, tool results cut short) and `history_search` (every session's text). Propose: `propose_skill`, `propose_memory`, `propose_mod` (only those for what Look for has on), `withdraw_proposal`. Nothing else, in any permission mode: no shell, no edits, no browser, no MCP tools, no sub-sessions, no schedules. Every proposal carries why and the sessions it is based on (ids that must exist).
- **Modes.** Approve (default): the dream finishes, then each proposal waits for Apply or Dismiss. Auto: a proposal is applied when it is made. Plan: nothing is applied; at the end the proposals become one plan in the dream's session (a "Dream plan" card, Apply all or Keep planning); approving it applies them all without another model call, and an answer in the session lets the dream withdraw or replace proposals and make a new plan.
- **Applying.** The app writes, never the model: a skill becomes `<project>/.silo-harness/skills/<name>/SKILL.md` or `~/.silo-harness/skills/<name>/SKILL.md`; memory lines go into the project's instructions file (the first of `SILOHARNESS.md`, `OPENHARNESS.md`, `OPENAGENT.md`, `OPENCODER.md`, `AGENTS.md`, `CLAUDE.md`, else a new `SILOHARNESS.md`) or `~/.silo-harness/SILOHARNESS.md` (`OPENHARNESS.md` there when only that one exists); a mod's folder is written to `<project>/.silo-harness/mods/<id>/` or `~/.silo-harness/mods/<id>/`, checked like every mod first, and stays off until you turn it on. Nothing else can be written. A proposal that changes an existing skill, mod or memory line must say so (and shows the difference); Apply refuses when the file changed since it was proposed. Revert puts back what was replaced (a file or folder as it was; memory line by line if you edited the file since). A proposal that holds what looks like a key, token or password, or a key from your settings, is refused.
- **The page.** **Projects** shows a card for each project that has dreams or that the next dream reads: its name, the mode, its last dream's closing report (or what it suggested), and the daily dream with what waits ("Daily at 03:00 · 2 suggestions waiting", "Off · last dream Nov 6", "… · 3 sessions to read"), with search, a filter (All, Waiting for you, Not dreamed yet) and a sort (last dream, name, latest activity). **Suggestions** lists every proposal that waits, by dream, as the cards a dream's session shows, with Apply, Dismiss and Apply all. The banner says whether the daily dream is on (Turn on; Change) and that a dream sends parts of your past sessions to the model; the gear opens the settings: the daily dream and its time, the mode, and what to look for (Skills, Mods, Memory). These apply to every project.
- **A project's page** (click its card): the breadcrumb "Dreaming / project ⌄", **Run a dream now**, then **History**, each dream newest first: when, how it started, its mode, how many sessions it read, and its state (running, waiting for you with the count, plan ready, applied, nothing to suggest, failed with the reason); a row opens the dream's session, where each proposal is a card with Apply, Dismiss or Revert. Beside it, the same settings, the project folder and a word on privacy and cost.
- **In the sidebar** a dream's session is listed only while it waits for you or is on screen, with a moon in front of its title and the waiting dot at the end; it stays in history, search and the trash like any session. The Dreaming row has a dot while suggestions wait. A daily dream that leaves proposals waiting sends a notification (when notifications are on). Settings no longer has a Dreaming section; a search there for it finds rows that open the page.
- A dream sends parts of your past conversations to the configured model and uses tokens.

## Mods

Panels in the right-hand rail, tabs beside the Browser, a strip above the composer, backgrounds, looks and slash commands are mods: folders of web files that run sandboxed and reload when a file is saved. The built-in ones (Environment, Context, Tasks, Plan, Outputs, Sub-sessions, Skills, Side chat, Scheduled) are written against the same protocol as yours. Settings → Mods has a tab per kind: Mods, Background, Chat bar and Conversation. The Mods tab lists what adds something (panels, tabs, strips, commands), each with its switch. The other three are looks, which have no switch: each tab shows the one in use in a preview, lets you click another version to try it there first, and Use applies it, one per kind (Default first; the background with your own picture and Dim). The first Use of a look of yours or of a project's asks for your approval, once. Settings → Appearance shows each look in use, with a row that opens its tab. **Delete all custom mods**, under the list on the Mods tab, moves every mod of yours (the folders in `~/.silo-harness/mods`) to the Trash after naming them; built-in mods and a project’s mods stay, and a look of theirs in use goes back to Default. Ask the agent to build one, or see [mods.md](mods.md). `node modkit/playground/serve.js` hosts mods outside the app while you work on them.

## History

- Every message, tool call, approval, plan and error is appended to `history/<session>.jsonl` in the data folder as it happens, and never rewritten: a rewind or a compaction adds a record. After a crash or a force-quit the session is restored from it, with a notice.
- Deleting a session moves it to a trash for 30 days (Settings → History: restore, delete now, change the period).
- Settings → History → **Delete all sessions** deletes every session at once, each the way a single delete does: into the trash for the period set there, or away at once when it is Off. Running sessions are stopped first, and the window opens on a fresh session.
- Search in the sidebar looks through titles, messages, tool calls and what compactions folded away.
- A session's menu exports it as Markdown; `history.export` also writes JSON or the raw log.

## Context and compaction

Near the limit (`compactThreshold`, 80% by default) old tool output is shortened first, which often is enough. Otherwise the older part of the conversation is summarised into a brief and the recent part is kept word for word; the brief carries your latest request verbatim and lists the files touched. A summary that would not be smaller is not used, and the session is never left over the limit. `/compact [focus]` does the same on demand. The Context panel shows what fills the window, slice by slice.

## Prompt caching

Every request starts with the same tools and system prompt, then the conversation so far. What changes during a session (the mode, the folder and date, the session's name) is a short note added to the conversation, so that start stays the same.

- **Anthropic** (a provider of type `anthropic`, or any base URL on `api.anthropic.com`): the app uses Claude's own Messages API and marks what to cache. The tools and the system prompt are kept an hour; the conversation is kept five minutes from its last use. Auto mode's check caches its instructions, the Auto mode notes and instruction files it is shown, and your earlier answers. Titles and the compaction summary use the OpenAI-compatible endpoint and are not cached.
- **Claude through a gateway** (OpenRouter, Portkey, Vercel, LiteLLM or another OpenAI-compatible one): the request asks for caching in the shape that gateway takes. A gateway that refuses it gets the request again without, for as long as the app runs.
- **OpenAI**: caches on its own; the app sends the session as `prompt_cache_key`, so a session's requests reach the same cache.
- **Others**: nothing extra is sent. Many cache a repeated start on their own.

Where the start is cached, old tool output is set aside in batches (past 90K tokens, or 60K after a pause of more than five minutes, down to 50K, or less in a small window) and old screenshots four at a time, so the cached part is rewritten seldom. Ollama and LM Studio keep pruning as before, and so does a session whose provider reports no cache read or write on three requests in a row sent within five minutes of the last reply, until it reports one. The context meter's detail says what share of the last request was read from the cache, when the provider reports it.

## Remote control

Settings → Remote control turns on a small web page, served by the app, for following and steering sessions from another device: read along live, send messages, stop a run, answer approval cards and plans, and allow an action Auto mode blocked. The browser's cards read as on the Mac ("Let the agent use example.com?", "Make a purchase?", with the model's reason and the amber note); the phone can allow a site once or for the session, never always. It is off until you turn it on, listens on this Mac only or on your network as you choose, and its links carry a long random token that you can replace. The remote cannot change settings, the permission mode, mods, schedules or trust, cannot save a project rule or a site, cannot answer the Browser pane's permission or download bars, and never receives a key. It is plain HTTP: use it on a network you trust.

## Providers

- **Ollama** (default): native `/api/chat` with `num_ctx`, thinking control and capability detection.
- **Gateway fields** (the `portkey` block) = any OpenAI-compatible endpoint, Portkey's by default. The window calls it Portkey for Portkey's own address and Gateway for any other.
- **Named providers**: any number of entries in `"providers"` of `settings.json` (or `config.json`), each of a type that knows its base URL, key variable and headers: `openrouter`, `portkey`, `openai`, `anthropic`, `groq`, `deepseek`, `together`, `ollama`, `lmstudio`, and `openai-compatible` for anything else. `"provider"` picks one by name. Settings → Model chooses among all of them and their models; the model button under the chat bar lists the provider's models and the other usable providers. The pill after it sets the reasoning effort, where the model takes one ([configure.md](configure.md#effort)).
- **The command line**: `silo` (in the app at `Contents/Resources/bin/silo`; Settings → General → Command line tool links it into `~/.local/bin`) adds, selects and tests providers and sets the other fields, for you or for a coding agent: `silo provider add openrouter --type openrouter --model … --use`, then `silo provider test`.
- All of it, with the shortest working example for each service, the field reference and the steps for coding agents: [configure.md](configure.md). Schema: [settings.schema.json](settings.schema.json).

### Retries

- **What is tried again**: a lost or refused connection, a stream that drops or sends nothing for 300 s (not on Ollama, where a local model may think long before its first token), and HTTP 408, 409, 429, 500, 502, 503, 504 and 529. Not: a bad request or key (400, 401, 403, 404, 413, 422), a request too long for the context (that compacts instead), an exhausted quota or billing, a Stop.
- **How often**: 6 tries in all. The waits start at 1 s and double to at most 30 s, each moved by up to 20%. A provider's `Retry-After` (or `retry-after-ms`) sets the wait instead; over 60 s, there is no retry and the error says when to try again ("Rate limited. Try again in 5 min.").
- **What you see**: one status line while it waits ("Connection lost. Retrying in 4 s (2 of 6)." or "Provider busy. …" for 429 and 5xx), gone when the reply starts. Text a dropped reply had shown is taken back; only the attempt that completes is kept and counted. When all 6 fail: "Could not reach the provider after 6 tries: …" with the provider's own message.
- **A reply cut at the output limit**: a tool call whose arguments were cut is not run (its result tells the model to send it in smaller pieces); a cut reply without calls is asked to continue, twice at most per message.
- **A call repeated with the same result**: the third time its result carries a note to try something else; the fifth time the run stops. Reading a terminal with `wait_ms` and listing sessions are exempt.

## Configuration

Settings is the place for all of it. On disk:

- Data folder `~/Library/Application Support/Silo Harness/`: `config.json`, `sessions/`, `history/`, `trash/`, `artifacts/` (with each session's images), `schedules.json`, `dreaming.json` (the dreams, their proposals, what applying replaced, the per-project cursors), mod storage, and the Browser pane's: `Partitions/browser/` (its profile: cookies, site data, cache) and `browser/` (`permissions.json`, the saved permission answers; `zoom.json`, the zoom per site; `downloads.json`, the downloads list without their contents; `profile.json`, the one-time profile note).
- Config folder `~/.silo-harness/` (or `SILO_HARNESS_CONFIG_DIR`): `settings.json`, `skills/`, `mods/`, `SILOHARNESS.md`.
- Before the app was renamed these were `~/Library/Application Support/Open Harness/`, `~/.open-harness/` (with `OPEN_HARNESS_CONFIG_DIR` and `OPENHARNESS.md`) and a project's `.open-harness/`. The first launch moves the two folders in your home and leaves a link at `~/.open-harness`; the old names in a project, the old file names and the old variables are still read when the new ones are absent.
- In a project: `.silo-harness/settings.json`, `.silo-harness/skills/`, `.silo-harness/mods/`, `.mcp.json`, and an instructions file (`SILOHARNESS.md`, `AGENTS.md` or `CLAUDE.md`).

A project's `.mcp.json` servers, its mods and its `settings.json` all stay off until you turn them on (a look of a project's applies only once you use it and approve it).

### settings.json

For providers and the command line, [configure.md](configure.md) supersedes this section.

`~/.silo-harness/settings.json`, then `<project>/.silo-harness/settings.json`, layer over `config.json`. Precedence: defaults < `config.json` < user < project.

```json
{
  "env": { "PORTKEY_API_KEY": "…" },
  "provider": "portkey",
  "portkey": { "baseURL": "https://gateway.example.com/v1", "model": "@vertex/gemini-2.5-pro", "contextWindow": 200000 }
}
```

- Settable: `provider`, `providers` (named providers, see [configure.md](configure.md)), `ollama.*`, `portkey.*`, `dreaming.*` (`daily`, `time` as `"HH:MM"`, `mode`: `auto`, `approve` or `plan`, and `skills`, `mods`, `memory`), `browser.*` (`keepCookies`, `downloadsDir`, `openChatLinksInPane`, `alwaysAllowed`, `sensitive`, `exempt`; a project's file may not set `alwaysAllowed` or `exempt`, see [configure.md](configure.md#the-browser)), `autoMode.*` (`environment`, `allow`, `model`; your own file only, see [configure.md](configure.md#auto-mode)), `permissionMode`, `maxTurns`, `sendScreenshotsToModel`, `systemPromptExtra`, `theme`, `autoTitles`, `autoCompact`, `compactThreshold`, `pruneToolResults`, `toolSet`, `toolActivity`, `notifications`, `keepAwake`, `historyTrashDays`, `env`, `hooks` and `disableAllHooks` (see [hooks.md](hooks.md)). `workingDirectory` in the user file is the folder the app opens in. An unknown key or a value of the wrong type is skipped and reported in Settings → Configuration files; the rest of the file applies.
- `env` is applied to the process environment, so a key can live there instead of in `config.json` (`PORTKEY_API_KEY` is a fallback for the gateway key). `${VAR}` and `${VAR:-default}` are expanded in every string. Variables a file set are put back when the file stops applying.
- **A project's file needs your approval.** Until you trust it in Settings → Configuration files nothing in it applies, and an edit withdraws the approval. A notice in the chat tells you one is waiting.
- **A project's file never carries, chooses or redirects a key**: `apiKey`, `apiKeyEnv`, `portkey.apiKey`, `portkey.providerApiKey`, `portkey.baseURL`, and `env` variables whose names end in `KEY`, `TOKEN`, `SECRET` or `PASSWORD` are ignored there with a problem line; an entry for a service that takes a key may not set its own `baseURL` (it is skipped whole), and a header may not hold a `${VAR}`. The type's usual variable is used, `portkey.model`, `virtualKey`, `provider` and `configId` still apply, and `ollama` or `lmstudio` may have an address. For a provider with another variable or address, define it in your own file and select it from the project with `"provider"`.
- `"$schema": "https://brandeispatrick.github.io/silo-harness/settings.schema.json"` gives an editor completion and checks.
- A field a file sets is read-only in Settings and is never written to `config.json`. Changes made while the app runs (the mode chip, the model chip) last until the files are read again.
- The files are read again when they change, when the folder changes, and when trust changes.

### Hooks

Commands and HTTP endpoints that run before and after the agent acts, written under `"hooks"` in either settings.json in Claude Code's format (a project's only once you trust its file), and mods with the `hooks` permission. Fired: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `Stop`, `SubagentStop`, `PreCompact`, `PostCompact`, `SessionEnd`. A PreToolUse hook can deny a tool call, force or skip the approval card, or rewrite its arguments; a Stop hook can send the run back to work. Tool names are Claude Code's where the tool is the same (`bash` is `Bash`, `read_file` is `Read`, …). Settings → Hooks lists the hooks in effect and the recent runs. The whole story, and what differs from Claude Code: [hooks.md](hooks.md).

## Keep awake

Settings → General: Off, While running (the default: system sleep is held off while a session runs; the display may still sleep), or Always.

## Security

The agent runs with your permissions: keep approvals on for untrusted tasks. Pages it reads are untrusted input. MCP servers are child processes with your permissions. `@` mentions send the file to the model. The built-in browser keeps a Chromium profile of its own, apart from the app's pages, artifacts and mods, with your sign-ins in it (kept across launches unless you turn Keep cookies off); the agent reads and acts in it with your sign-ins, so each site asks you first (in Auto mode the safety check decides, and asks you when unsure), sensitive sites ask before every action, and purchases, new accounts and its downloads always ask (see Browser). What you or the agent type into a password, one-time code or card field never reaches the agent, the transcript or hooks: the browser tools show `•••` in its place, the agent may not type into such a field away from your own development hosts, and a screenshot is refused while such a field is focused and filled or shows its value. A page that wants your camera, microphone, location, notifications or the like asks you on a bar under the URL bar that neither the agent nor the phone page can answer; full screen and copying to the clipboard are allowed without asking, USB, HID and serial devices never, and "every time" and "Don't allow" are kept per site until you reset them. Page content is data to the agent, fenced and with hidden text left out; an HTML artifact cannot send anything out. A certificate error stops the page; only you can proceed past it. What a repository brings with it (MCP servers, a settings file, mods) is never applied without you turning it on. Mods run in sandboxed frames with the permissions you grant, cannot reach the network without the `network` permission, and can never answer an approval card or change the permission mode; a mod that contributes styles restyles the app itself, so treat it like a theme from someone you trust. Remote control exposes sessions to whoever holds the link.

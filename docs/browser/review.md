# The browser spec, read again before building

A second pass over [spec.md](spec.md) and [research.md](research.md), made against the code on `browser-safety` (b9f7050, which carries `cleanup` and the 0.9.1 fixes) and against Electron 45.0.0's own typings in `node_modules/electron/electron.d.ts`. The user accepted all thirteen recommendations in spec §6; this pass keeps them and changes how a few are carried out. Where it disagrees with the spec, this document wins; the spec stays as the record of the options.

## 1. What holds

- **Every Electron API the spec leans on exists in 45.0.0**, checked by name in the typings: `WebContentsView` with `View.setVisible` and `contentView.removeChildView`; `setWindowOpenHandler` returning `{ action: 'allow', createWindow }` where `createWindow(options) => WebContents`; `session.fromPartition`, `setPermissionRequestHandler`, `setPermissionCheckHandler`, `setDevicePermissionHandler`, `setSpellCheckerEnabled`, `clearStorageData`, `clearCache`, `clearAuthCache`; `app.on('certificate-error', (event, webContents, url, error, certificate, callback, isMainFrame))`; `will-download` with `DownloadItem.setSavePath`, `getFilename`, `getMimeType`, `getReceivedBytes`, `getTotalBytes`; `findInPage` and `found-in-page`; `setZoomLevel`; `printToPDF`; `inspectElement`; `navigationHistory`; `enableDeviceEmulation`. For Phase 2: `safeStorage.encryptStringAsync`, `decryptStringAsync` and `isAsyncEncryptionAvailable` are there and the sync ones are marked deprecated, as the research says; `app.configureWebAuthn` and the `select-webauthn-account` event are there; `systemPreferences.canPromptTouchID` and `promptTouchID` too.
- **The ranked list in research §11 and the three phases are the right cut.** Nothing in the list is misplaced, and the 0.9.1 branch already covers the two cheapest items in Phase 1 (hiding credential values; asking before camera, microphone, location, notifications).
- **The code is ready for it.** `BrowserController` is one class with the in-page scripts beside it (596 lines); the safety world and `credentialKind` detection in `browser-safety.ts` are reusable as they are; the tools in `src/main/tools/browser.ts` go through one `guarded()` wrapper where a site check slots in; the approval card (`agent.ts` `ask()`, `agent/permissions.ts` `decideApproval`, renderer `approvals.ts`) has the scopes we need (once, session, a wider saved one) and a `custom` kind with Allow and Deny only; features register RPC methods through `app.rpc.handle` with a contract file in `src/shared/` (`hooks.ts` is the pattern); the live rig can already reach the pane's page as a second CDP target and the main process through `--inspect` (`test/live/browser-safety.js` does both).

## 2. What changes

Numbered against the spec's sections and decisions.

1. **Nobody gets signed out (decision 1).** The move to `persist:browser` copies the cookies over instead of starting fresh: on the first run with the new partition, `session.defaultSession.cookies.get({})` → `browserSession.cookies.set(…)` for each (url built from the domain, path and `secure`; a `hostOnly` cookie is set without `domain`; `httpOnly`, `expirationDate` and `sameSite` carried; session cookies too), then the default session's http(s) cookies are cleared, so the app's own pages, artifacts (model-written HTML) and mod pages no longer share a jar with the user's sign-ins. What cannot be copied is `localStorage` and IndexedDB (no Electron API), so a site that keeps its token there asks again. One quiet line under the URL bar, once: "The browser now keeps a profile of its own. Sign-ins came along; a few sites may ask again."
2. **Local files are not exempt (spec 3.2 "Exempt").** The spec exempts `file:` pages from approval. For the agent, `browser_navigate` to a `file:` URL is a file read that goes around the file tools' guard. Rule: a `file:` navigation by the agent asks (the card shows the path) unless the path is inside the session's working directory, where `read_file` is free anyway. `artifact:` stays exempt (the model wrote it). `javascript:`, `data:`, `blob:`, `chrome:`, `devtools:` and `about:` other than `about:blank` are refused outright with "use create_artifact for a page of your own".
3. **One site card covers reading too (spec 3.2 "Approvals").** The first `browser_*` call that touches a site the user has not approved shows the card, reading tools included: reading is where a prompt injection enters, and Claude Code asks per site before reading as well. "Allow once" is that one call; "Allow example.com for this session" (A) and "Always allow example.com" (P, saved on this Mac, listed in Settings → Browser) are one key away. Within an approved site, reading and acting run without cards, apart from the rules below. In Plan mode the reading tools are offered (`readOnly: true`), the acting ones are not, and the site card still appears for a new site, because a navigation can carry data out in its URL.
4. **Tools act on the active tab only (spec 3.2 "Agent tools").** No optional `tab_id` on every tool: `browser_tabs` lists, opens, selects and closes, and everything else works on the tab the user sees. What the agent reads is what the user is looking at. The tabs belong to the pane, not to a chat session; the foreground-session rule stays as it is.
5. **`browser_eval` (decision 10).** Ask mode asks for every call, even on an approved site, with the code on the card. Auto mode asks when a plain guard, `guardEval(code)` in the policy module, sees the code reach for site data or send it: `document.cookie`, `localStorage`, `sessionStorage`, `indexedDB`, `caches`, `fetch(`, `XMLHttpRequest`, `sendBeacon`, `WebSocket`, `EventSource`, `postMessage`, `import(`, `.value` of an input, `password`, `token`, `credential`, `location =`/`location.href =`/`window.open`. Bypass runs it. The result is redacted as today.
6. **Decision 3's "never" list becomes two lists.** *Never* (a refusal the model reads, in every mode, Bypass included): typing or pressing character keys into a password, one-time code or card field on a site that is not exempt ("Ask the user to sign in in the pane"); answering a permission bar; proceeding past a certificate error; solving a CAPTCHA (a click inside a reCAPTCHA, hCaptcha or Turnstile frame or widget); the navigations in item 2. *Always ask*, with a card that has Allow and Deny only, in every mode Bypass included, because money and accounts are the user's: a click that looks like a purchase (a button whose text matches "pay now", "place order", "buy now", "complete purchase", "confirm payment", "checkout", or a submit inside a form with card fields, or a form posting to a payment host) and a click that looks like account creation ("create account", "sign up", "register"). A download the agent started is in this second list too (item 9). Claude Code's own words are "won't purchase items, create accounts, or bypass CAPTCHAs without your input": the first two are cards, the third is a refusal. On exempt hosts (`localhost`, `127.0.0.1`, `[::1]`, `*.localhost`, `*.test`, and the user's own list in Settings → Browser) the agent types into credential fields as 0.9.1 lets it, with the text hidden, so the user's own app under development can be tested with test accounts.
7. **Sensitive sites: a short built-in list plus a page signal.** Hostname patterns in `policy.ts`, editable in Settings → Browser: identity providers (`accounts.google.com`, `login.microsoftonline.com`, `login.live.com`, `appleid.apple.com`, `account.apple.com`, `*.auth0.com`, `*.okta.com`, and the host prefixes `login.`, `auth.`, `sso.`, `id.`, `accounts.`, `signin.`), webmail (`mail.google.com`, `outlook.live.com`, `outlook.office.com`, `outlook.office365.com`, `mail.yahoo.com`, `mail.proton.me`, `fastmail.com`, `icloud.com`, the prefix `mail.`), banks, brokers and wallets (`paypal.com`, `venmo.com`, `chase.com`, `wellsfargo.com`, `bankofamerica.com`, `citi.com`, `capitalone.com`, `americanexpress.com`, `schwab.com`, `fidelity.com`, `vanguard.com`, `robinhood.com`, `coinbase.com`, `binance.com`, `kraken.com`, `revolut.com`, `wise.com`, `*.gov`, `*.gov.uk`, and any host with the word `bank`), payment pages (`checkout.stripe.com`, `pay.google.com`, the prefixes `checkout.`, `pay.`, `*.adyen.com`, `*.braintreegateway.com`), and password managers' vaults (`vault.bitwarden.com`, `my.1password.com`, `lastpass.com`, `passwords.google.com`). On top of the list, a page with a password field is a sign-in page: the agent's first acting call on it asks once. On a sensitive site every acting call asks (reads do not), in every mode but Bypass, with the amber note "This looks like a sign-in, email or financial site" on the card.
8. **Permission bar, Chrome's way (spec 3.3, replacing 0.9.1's dialog).** The native modal dialog of 0.9.1 becomes a bar under the URL bar, with the three answers Chrome gives: **Allow this time** (until the tab leaves the site), **Allow every time** (saved) and **Don't allow** (saved too; Settings → Browser → Permissions resets any of them). No "Remember" checkbox. The bar belongs to its tab and waits while the tab is in the background. The answer travels with a nonce the renderer got from the main process, so no tool can answer. The policy table stays as 0.9.1 has it (full screen and clipboard writes free, `geolocation` denied for want of a Google key, the rest asked), and `setDevicePermissionHandler` denies USB, HID and serial.
9. **Downloads: the agent's go through a card (decision 4).** `will-download` saves user-started downloads to `~/Downloads` (or the folder chosen in Settings) under a sanitised, unique name, listed in a tray in the browser bar with Show in Finder, Open, Cancel and Clear. A download that begins while a browser tool call is acting (the controller knows, with a two-second tail) is paused and asked for on a card with Allow and Deny only: "Download report.pdf (1.2 MB) from example.com?"; Deny cancels it. Executable types are not special: every agent download is asked for one by one, which is what Claude in Chrome does.
10. **The certificate page is drawn by the pane, not served from a scheme (spec 3.2 `certificates.ts`).** On `certificate-error` for a tab's main frame the default (reject) stands; the tab records `{ host, code, fingerprint }` and the renderer covers the tab's slot with the interstitial from the spec's 3.3 (triangle, "This connection is not private", the host, the code in words, **Go back**, "Proceed anyway (unsafe)" as a text link). Proceed is an RPC the renderer alone calls; it remembers host and fingerprint for this app run and reloads. The agent's result reads "The certificate for host is not valid (code). Only the user can proceed." No `silo-browser://` scheme.
11. **Popups (spec 3.2 `popups.ts`): as written, with two notes to verify on the build.** `createWindow` returns the `WebContents` of a `WebContentsView` made in the same partition and laid over the pane as the floating card; the opener relation and `postMessage` are expected to work because Electron created the contents for the page's own `window.open`. **[verify]** that a popup closing itself (`window.close()`) tears the view down, and that Google's, GitHub's and Microsoft's sign-in popups complete; if a site insists on a top-level window (`screenX`, `outerWidth`), fall back to a real child `BrowserWindow` in the same partition. Electron has no popup blocker of its own: deny a fourth open popup and say so in the strip.
12. **Settings live in the config, decisions on disk.** The user-edited lists and switches are `AppConfig.browser` (`keepCookies`, `downloadsDir`, `openChatLinksInPane`, `alwaysAllowed: string[]`, `sensitive: string[]`, `exempt: string[]`), so Settings → Browser binds rows to fields like every other section and `docs/settings.schema.json` is regenerated. Per-site permission answers, zoom levels and the download list are the browser's own files under `userData/browser/`. "Open links from the chat in the pane" is off by default (today's behaviour, links open in the default browser), one switch away.
13. **Keyboard.** ⌘⇧N new tab and ⌘W close tab when the pane has focus (decision 2), ⌘F find in page when the browser view has focus (the composer's ⌘F still searches sessions), ⌘+ ⌘− ⌘0 zoom. Check `src/renderer/shortcuts.ts` for what ⌘W does today before taking it.

Everything else in the spec's Phase 1 stands: the tab strip, URL pill, find bar, downloads tray, popup card, blocked-popup strip and Settings → Browser as drawn in 3.3; tabs capped at 12 with a notice; zoom per origin; the context menu; print and Save as PDF; DevTools; the `reason` parameter on the acting tools shown in grey under the action; the redirect re-check (which item 3 makes automatic: every call checks the active tab's site); the system prompt line.

## 4. How Phase 1 is built

Phase 1 is built on `browser-phase1`, in the four stages of §4, and ships as 0.10.0 after 0.9.1.

**Built.** The own profile with the cookie migration and its note, Keep cookies, Clear browsing data; tabs (cap 12, ⌘⇧N ⌘W ⌘L) and `browser_tabs`; popups as floating cards, a fourth refused with the blocked-popup strip and Show; the per-site approvals with `reason`, local files, refused schemes, sensitive sites and the sign-in page signal with the amber note, the refusals (credentials, also after a click moved the focus; CAPTCHAs) and the Allow/Deny cards (purchases, accounts), `browser_eval` per mode, plan mode's read-only set; the permission bar with its three answers and saved store, USB/HID/serial refused; the certificate interstitial and the URL pill's lock, Not secure and amber triangle; downloads with sanitised names, the tray, and the agent's download bar; find in page, zoom per site (kept by host, as Chromium's own zoom map is, in `userData/browser/zoom.json`) with the chip, the View menu's zoom routed so exactly one thing zooms; the native context menu with Print…, Save as PDF… and Inspect Element, ⌥⌘I; chat links in the pane; Settings → Browser; the phone's browser cards.

**Verified headless** (`npm test`): the policy, approvals, popups, permissions, certificates, downloads, session and safety suites, and `browser-polish.js` (find steps and results, zoom steps and store, the View menu's routing, the context menu template, the in-page shortcuts, chat-link routing, browser_type's refusal after the focus moves), `remote.js` (a browser card reaches the phone whole; no route answers the bars). **Verified live** in the hidden window on the mock model: `browser-tabs`, `browser-oauth`, `browser-approvals`, `browser-safety`, `browser-permissions`, `browser-cert`, `browser-downloads`, `browser-polish` (find with ⌘F sent through the main process's input path, zoom across a relaunch and the chip, the blocked-popup strip, chat links off and on, the typing refusal, the context menu's labels), and `remote-page` with two browser cards.

Not done: review item 4 (Auto mode's classifier for browser actions) and 15 (approvals keyed by scheme), which need `src/main/agent/`; WebRTC from an artifact, which Chromium's CSP has no directive for (`webrtc 'block'` is ignored).
